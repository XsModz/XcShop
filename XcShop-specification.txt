SECTION 5 — KEY SYSTEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Implement a redeemable key system usable by admins and resellers.

Key types:
  VIP_1D   — grants 1 day VIP
  VIP_7D   — grants 7 days VIP
  VIP_30D  — grants 30 days VIP
  VIP_LIFE — grants lifetime VIP
  FILE_ID  — grants access to a single specific file

Key properties stored in PostgreSQL:
  - key string (unique, cryptographically random, URL-safe)
  - key type
  - target file_id (nullable, only for FILE_ID keys)
  - created_by (user_id of admin or reseller who generated it)
  - redeemed_by (user_id, nullable)
  - redeemed_at (timestamptz, nullable)
  - expires_at (timestamptz, nullable — key itself can expire unused)
  - max_uses (integer, default 1)
  - use_count (integer, default 0)
  - is_active boolean

Admin commands:
  /genkey VIP_7D 5          — generate 5 x 7-day VIP keys
  /genkey VIP_LIFE 1        — generate 1 lifetime key
  /genkey FILE 88 3         — generate 3 keys for file ID 88
  /keyinfo KEY_STRING       — inspect a key
  /revokekey KEY_STRING     — deactivate a key
  /listkeys                 — paginated list of all keys with status

Reseller commands (if caller has reseller role):
  /genkey VIP_7D 2          — only allowed key types reseller can generate
                              are defined per reseller in their config
  /mykeys                   — list keys the reseller created
  /keystats                 — count used / unused in reseller's pool

Redemption flow:
1. User taps 🔑 Redeem Key and pastes the key string.
2. System checks: key exists, is_active, not expired, use_count < max_uses.
3. System checks: this user has not already redeemed this key if max_uses=1.
4. Apply the grant atomically inside a transaction.
5. Increment use_count, set redeemed_by and redeemed_at if max_uses=1.
6. Confirm success to the user.

Implement a multi-instance architecture allowing one deployment to serve
multiple logical "shops" under different bot tokens.

Instance properties stored in PostgreSQL:
  - id (serial)
  - name (display name)
  - bot_token (encrypted at rest using AES-256-GCM, key from ENCRYPTION_KEY env)
  - admin_id (BIGINT, Telegram user who owns this instance)
  - storage_chat_id (BIGINT)
  - support_username (TEXT)
  - webhook_secret (TEXT)
  - is_active boolean
  - created_at

Single-instance mode (default):
  BOT_TOKEN, ADMIN_ID, STORAGE_CHAT_ID are read from environment variables.
  The instances table has one row. All features work as described elsewhere.

Multi-instance mode (opt-in, enabled by MULTI_INSTANCE=true env var):
  The webhook endpoint reads the bot token from the URL path:
    /api/webhook/[instance_id]
  Each request loads the correct instance config from the database.
  Decrypts the bot token in memory only, never logs it.
  All data (users, files, categories, keys, resellers) is scoped to
  instance_id via a foreign key on every relevant table.

Super-admin commands (only the SUPER_ADMIN_ID env var can invoke these):
  /addinstance NAME ADMIN_ID STORAGE_CHAT_ID
  /removeinstance INSTANCE_ID
  /listinstances
  /instanceinfo INSTANCE_ID
  /setinstancetoken INSTANCE_ID BOT_TOKEN

Each instance admin can manage their own instance's users, files,
categories, VIP, keys, and resellers, but cannot see or touch other
instances.

In single-instance mode, ignore all instance routing logic and treat
the single environment-variable config as the only instance. The
instances table is still created but not actively used for routing.

Encryption:
  Provide a lib/crypto.js module with:
    encryptToken(plaintext) → { iv, ciphertext, tag } stored as JSON string
    decryptToken(storedJson) → plaintext
  Use Node.js built-in crypto module only. No third-party crypto libraries.

SECTION 9 — FILE UPLOAD WORKFLOW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Admin sends a file to the bot with caption format:
  free | CategoryName | File Title
  vip  | CategoryName | File Title

Bot must:
1. Verify sender is ADMIN_ID.
2. Validate caption format strictly.
3. Trim and validate title (1–128 chars).
4. Locate or create category atomically (INSERT ... ON CONFLICT DO NOTHING).
5. Copy message to STORAGE_CHAT_ID via copyMessage.
6. Insert file record into PostgreSQL inside a transaction.
7. On any failure: rollback DB, and if storage copy succeeded but DB
   failed, attempt to delete the storage message and log the outcome.
8. Confirm with file ID and storage message ID on success.
9. On bad caption: reply with the correct format example.

Supported media: document, photo, video, audio, voice, animation.
